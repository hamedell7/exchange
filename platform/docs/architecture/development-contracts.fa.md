# قراردادهای توسعه Exchange

**وضعیت:** قرارداد جاری توسعه  
**دامنه:** همه سرویس‌های Monorepo

این سند مبنای تصمیم‌های توسعه Exchange است. هدف، معماری قابل نگهداری با کمترین لایه و abstraction لازم است؛ نه پیاده‌سازی الگوهای معماری صرفاً برای آمادگی احتمالی آینده.

## ۱. معماری و اصول پایه

- معماری کلان Exchange از Microserviceهای مستقل تشکیل شده است. هر سرویس مالک داده، مدل، Migration، دیتابیس، API، تنظیمات و چرخه استقرار خودش است.
- ساختار داخلی سرویس‌های Laravel بر پایه **Service-Based Architecture و conventionهای خود Laravel** است.
- مسیر معمول درخواست: Route → Controller → Form Request → Service → Eloquent / Query Builder / Laravel Facades. خروجی از طریق API Resource یا پاسخ HTTP صریح برگردانده می‌شود.
- Service منطق و هماهنگی یک قابلیت منسجم را نگه می‌دارد. Controller نازک است. Eloquent Model روش استاندارد دسترسی و نگهداری داده است.
- Serviceها مجازند مستقیماً از Eloquent، `DB::transaction`، `Hash`، `Mail`، `Cache`، `Http` و سایر امکانات Laravel استفاده کنند. برای پوشاندن این امکانات، لایه‌های موازی و Interface اجباری ایجاد نمی‌کنیم.
- هیچ سرویس دیگری Eloquent Model، جدول یا دیتابیس سرویس مالک را import یا query نمی‌کند.
- هر قانون باید یک مالک مشخص داشته باشد. یک قانون را در چند لایه با رفتارهای متفاوت تکرار نمی‌کنیم.
- سادگی پیاده‌سازی همراه با حفظ invariant، امنیت و مرزبندی سرویس‌ها بر الگوی ظاهری اولویت دارد.

## ۲. ساختار داخلی Laravel

ساختار معمول پیشنهادی:

    app/
    ├── Http/
    │   ├── Controllers/
    │   ├── Requests/
    │   ├── Resources/
    │   └── Middleware/
    ├── Models/
    ├── Services/
    │   └── <Capability>/
    ├── Enums/
    ├── Exceptions/
    ├── Support/
    ├── Mail/
    └── Providers/

این درخت الگوی راهنما است، نه الزام به ایجاد همه پوشه‌ها. پوشه‌ای که کد واقعی ندارد ساخته نمی‌شود. از ساختار پیش‌فرض Laravel دور نشوید مگر اینکه اندازه یا ماهیت یک قابلیت دلیل مشخصی برای سازمان‌دهی متفاوت ایجاد کند.

### مسئولیت‌ها

**Controller**
- ورودی را از Form Request معتبر تحویل می‌گیرد.
- Service مربوط به قابلیت را فراخوانی می‌کند.
- status code و پاسخ HTTP را مشخص می‌کند.
- منطق چندمرحله‌ای کسب‌وکار و queryهای پیچیده را در خود نگه نمی‌دارد.

**Form Request**
- نوع، قالب، الزامی بودن، طول، تأیید رمز و فیلدهای مجاز ورودی HTTP را بررسی می‌کند.
- فیلدهای انتقالی مثل `password_confirmation` را به Service منتقل نمی‌کند.
- برای مسیرهایی که فقط از HTTP فراخوانی می‌شوند، محل اصلی اعتبارسنجی ورودی است. اگر یک invariant باید از مسیر Queue یا Console هم حفظ شود، خود Service نیز آن را enforce می‌کند.

**Service**
- یک قابلیت یا عملیات منسجم را هماهنگ می‌کند.
- عملیات چندمرحله‌ای، کنترل وضعیت و تراکنش‌های لازم را اجرا می‌کند.
- برای query ساده از Eloquent / Query Builder استفاده می‌کند.
- یک Service بزرگ برای کل سیستم نسازید و برای هر متد trivial نیز Service جدا تولید نکنید.
- کلاس کمکی فقط زمانی استخراج می‌شود که مسئولیت مستقل و استفاده مجدد واقعی داشته باشد.

**Eloquent Model**
- مالک casts، relations، scopes، mass-assignment policy و رفتارهایی است که واقعاً به مدل رکورد تعلق دارند.
- استفاده مستقیم Service از Model طبیعی است؛ Repository اجباری برای wrap کردن Eloquent نداریم.
- فیلدهای حساس با hidden محافظت می‌شوند، ولی پاسخ API همچنان باید allow-list صریح داشته باشد.

**API Resource**
- فیلدهای قابل انتشار به مصرف‌کننده را صریحاً تعیین می‌کند.
- Model یا خروجی query بدون کنترل به API serialize نمی‌شود.
- برای هر Resource، DTO خروجی موازی نسازید مگر اینکه قرارداد مستقل و استفاده واقعی آن را توجیه کند.

**Provider**
- برای تنظیمات و ثبت bindingها یا boot کردن قابلیت‌های Laravel است؛ نه محل منطق کسب‌وکار.
- Serviceهای معمول concrete به DI container لاراول نیاز ندارند که حتماً در Provider ثبت شوند؛ auto-resolution کافی است.

## ۳. Service، Repository، Interface و DTO

هیچ‌کدام از این abstractionها صرفاً به‌دلیل الگو بودن اجباری نیستند.

- **Repository:** وقتی جداسازی persistence ارزش مشخصی دارد، چند روش ذخیره‌سازی واقعی وجود دارد یا عملیات دسترسی پیچیده و تکرارشونده است. صرفاً wrap کردن `User::query()` یا `DB::table()` Repository مفیدی نمی‌سازد.
- **Interface:** وقتی مرز واقعی جایگزینی، یکپارچه‌سازی بیرونی یا چند پیاده‌سازی وجود دارد. برای هر Service، Model، Facade یا کلاس concrete یک Interface موازی نسازید.
- **DTO:** وقتی ورودی/خروجی قرارداد مستقل، پیچیده، immutable یا مشترک بین چند مصرف‌کننده دارد. برای انتقال چند scalar از Controller به Service یک Command DTO نسازید.
- **Value Object:** وقتی یک مفهوم معنای مستقل، رفتار یا اعتبارسنجی قابل استفاده مجدد دارد. برای هر ستون یا primitive یک Value Object تولید نکنید.
- **Domain Model مستقل از Eloquent:** پیش‌فرض همه قابلیت‌ها نیست. برای عملیات ساده و CRUD، Eloquent Model + Service کافی است. اگر بخشی مانند Ledger، Order Matching یا وضعیت پیچیده حساب invariantهای متعدد و transitionهای دشوار داشت، منطق آن قابلیت می‌تواند در کلاس‌های تخصصی کوچک و مستقل مدل شود؛ بدون تحمیل چهار لایه به کل سرویس.
- **CQRS:** تفکیک جداگانه read/write مدل، Handler، Read Model یا دیتابیس پیش‌فرض نیست. query ساده در Service همان قابلیت قرار می‌گیرد. در صورت وجود نیاز اندازه‌گیری‌شده به read model مستقل یا بار متفاوت خواندن، CQRS جداگانه ارزیابی می‌شود.
- **Events / Jobs:** برای کار غیرهمزمان یا ارتباط بین سرویس‌ها بر اساس نیاز واقعی‌اند، نه برای هر متد.

## ۴. اعتبارسنجی، خطا و HTTP

- Form Request شکل ورودی HTTP را اعتبارسنجی می‌کند؛ Service مسئول قواعدی است که باید در هر مسیر فراخوانی حفظ شوند.
- خطای ورودی نامعتبر باید با پاسخ 422 و قالب استاندارد Laravel شامل `message` و `errors` برگردد.
- تعارض مشخص با وضعیت یا قید یکتا، مانند ایمیل ثبت‌شده، 409 است.
- خطای دیتابیس، SQL، Stack Trace، Secret و جزئیات داخلی در پاسخ API افشا نمی‌شود.
- فقط constraint مشخصی مثل `users_email_normalized_unique` به خطای تکراری بودن ایمیل نگاشت می‌شود؛ همه `QueryException`ها را به 409 تبدیل نکنید.
- خطاهای ناشناخته باید به 500 عمومی منتهی شوند و جزئیات فقط در لاگ امن ثبت شوند.

| وضعیت | معنا |
|---|---|
| 201 | منبع با موفقیت ایجاد شد |
| 400 | درخواست از نظر ساختار/پروتکل قابل پردازش نیست |
| 401 | احراز هویت لازم است یا معتبر نیست |
| 403 | هویت معتبر است اما مجوز ندارد |
| 404 | منبع وجود ندارد یا در دسترس نیست |
| 409 | تعارض با وضعیت فعلی منبع |
| 422 | ورودی قابل پردازش است اما اعتبارسنجی را نمی‌گذراند |
| 429 | محدودیت نرخ درخواست |
| 500 | خطای غیرمنتظره، بدون جزئیات داخلی |

قرارداد دقیق هر endpoint در OpenAPI همان سرویس ثبت می‌شود. Resource فقط فیلدهای مجاز را برمی‌گرداند؛ حتی اگر Eloquent Model از hidden attributes استفاده کند.

## ۵. قرارداد داده و دیتابیس

- PostgreSQL دیتابیس اصلی سرویس‌های Exchange است؛ تست SQLite مکمل سریع است، نه جایگزین تست رفتار PostgreSQL.
- قیدهای Unique، Foreign Key و Check برای invariantهای وابسته به concurrency الزامی‌اند.
- تراکنش برای چند تغییر وابسته‌ای استفاده می‌شود که باید با هم Commit/Rollback شوند؛ برای یک Insert، Unit of Work یا abstraction تراکنش نسازید.
- از `DB::transaction` در Service استفاده کنید. برای row lock و conditional update از امکانات خود دیتابیس/Laravel استفاده می‌شود.
- Migration باید یک تغییر Schema منسجم را نمایش دهد و نام قیدهای مهم صریح و پایدار باشد.
- برای داده پولی از float استفاده نکنید؛ نوع و scale/واحد پول باید در قرارداد همان قابلیت روشن باشد.
- داده Ledger پس از ثبت Append-only است؛ اصلاح با سند معکوس/اصلاحی انجام می‌شود، نه ویرایش بی‌ردپای رکورد مالی.

### سیاست ایمیل Identity

- local-part ایمیل برای نمایش و ارسال با همان casing ورودی حفظ می‌شود؛ دامنه هنگام ذخیره lowercase می‌شود.
- برای شناسه حساب، Exchange عمداً کل ایمیل را case-insensitive در نظر می‌گیرد.
- کلید مقایسه با lowercase کل آدرس ساخته می‌شود. دیتابیس آن را از مقدار اصلی تولید و روی آن Unique Index اعمال می‌کند؛ برنامه نباید تنها مرجع این قاعده باشد.
- Migration پیش از تغییر Schema وجود ایمیل‌های تکراری پس از نرمال‌سازی را بررسی می‌کند و در صورت وجود، بدون حذف/ادغام خودکار داده‌ها متوقف می‌شود.
- هر Use Case ورود/بازیابی/تغییر ایمیل باید از همین کلید مقایسه استفاده کند. جست‌وجوی خام روی ستون `email` برای شناسایی حساب کافی نیست؛ از `email_normalized` استفاده کنید.
- قبل از اعطای امکان واریز، برداشت یا معامله، تأیید مالکیت ایمیل و وضعیت حساب باید در سیاست دسترسی بررسی شود.

### سیاست رمز عبور Identity

- تا وقتی MFA برای حساب فعال و اجباری نشده، حداقل رمز ۱۵ کاراکتر است. سقف ورودی ۱۲۸ Unicode code point است.
- رمز باید با کاراکترهای قابل‌چاپ ASCII، فاصله و Unicode کار کند؛ هر code point یک کاراکتر شمرده می‌شود.
- ترکیب اجباری حروف بزرگ/کوچک، عدد یا نماد و تغییر دوره‌ای اجباری رمز اعمال نمی‌کنیم.
- Hashing در Identity با Argon2id انجام می‌شود. Docker Build و CI باید وجود پشتیبانی واقعی Argon2id در PHP را بررسی کنند؛ در صورت نبود پشتیبانی، Build/Test باید fail شود و fallback نکنند.
- هزینه Argon2id باید با بار واقعی سرور و محدودیت نرخ درخواست تنظیم و پایش شود.
- پیش از انتشار عمومی Production، بررسی رمز در برابر فهرست معتبر رمزهای رایج/افشاشده باید طراحی و اضافه شود؛ یک فهرست کوتاه hard-code شده معادل این بررسی نیست.
- این سیاست در Register، Login، Password Reset و Password Change یکسان است.

## ۶. قرارداد سرویس‌به‌سرویس

- ارتباط بین سرویس‌ها فقط از API Gateway/HTTP داخلی یا Integration Event نسخه‌دار انجام می‌شود.
- خواندن دیتابیس سرویس دیگر، Cross-database query و Foreign Key بین دیتابیس‌ها ممنوع است.
- شناسه کاربر/منبع سرویس مالک، مرجع خارجی است؛ مدل Eloquent یا مدل داخلی آن به سرویس مصرف‌کننده منتقل نمی‌شود.
- OpenAPI قرارداد HTTP و فایل‌های زیر `platform/contracts/openapi/<service>` مرجع شکل درخواست/پاسخ هستند.
- Eventها Schema نسخه‌دار دارند و حداقل شامل `event_id`، `event_type`، `schema_version`، `occurred_at`، `correlation_id` و payload مشخص‌اند.
- انتشار Event وابسته به تغییر دیتابیس باید با Transactional Outbox اتمیک شود، زمانی که انتشار قابل اتکا وارد نیاز محصول شود.
- مصرف‌کننده Event باید Idempotent باشد؛ تحویل تکراری پیام نباید عملیات مالی یا تجاری را تکرار کند.
- تغییر ناسازگار API/Event باید نسخه یا دوره سازگاری و برنامه مهاجرت داشته باشد.

## ۷. قواعد ویژه Wallet و Trading

این اصول از ابتدا اجباری‌اند؛ ساختار کلاس‌ها فقط پس از تعریف Use Case و invariantهای دقیق انتخاب می‌شود.

### Wallet
- Amount با integer در کوچک‌ترین واحد پول یا Decimal با precision/scale صریح نگهداری می‌شود؛ هرگز float.
- Ledger منبع حقیقت حرکت پول است؛ Balance مشتق‌شده یا materialized باید با Ledger قابل تطبیق باشد.
- هر عملیات مالی شناسه Idempotency پایدار و قید دیتابیس متناسب دارد.
- رزرو، آزادسازی، برداشت و انتقال باید در برابر Race Condition و Double Spend محافظت شوند.
- چند ثبت وابسته باید در مرز تراکنش واحد انجام شوند؛ قفل‌گذاری/سطح Isolation براساس الگوی واقعی عملیات انتخاب می‌شود.
- Ledger entry و رویداد مالی منتشرشده پس از ثبت، ویرایش/حذف بی‌ردپا نمی‌شوند.

### Trading
- Order چرخه وضعیت صریح و transitionهای مجاز دارد.
- قیمت، مقدار، Tick Size، Step Size و ارزش مالی با دقت عددی مشخص کار می‌کنند؛ float ممنوع.
- اجرای معامله و Execution Record تغییرناپذیر و قابل ردیابی است.
- ارتباط با Wallet از قرارداد رزرو/آزادسازی وجه می‌گذرد؛ Trading مستقیماً دیتابیس Wallet را تغییر نمی‌دهد.
- هر سفارش ورودی/فرمان خارجی شناسه idempotency یا client order id و رفتار تکرار دقیق دارد.
- منطق Matching و ترتیب اجرای سفارش‌ها deterministic و قابل تست طراحی می‌شود.

## ۸. قرارداد تست و کیفیت

- Feature Test رفتار endpoint کامل را از ورودی تا Service، دیتابیس و پاسخ عمومی بررسی می‌کند.
- برای Serviceهایی که منطق مستقل و غیرساده دارند Unit Test بنویسید؛ Mock کردن هر Facade یا هر Eloquent call هدف نیست.
- Integration Test روی PostgreSQL برای Mappingهای مهم، Unique/Check constraint، Transaction، Locking و رفتار وابسته به driver لازم است.
- تست‌های HTTP باید validation، status، response allow-list، Authentication، Rate Limit و فیلدهای ناشناخته را پوشش دهند.
- تست رد رمز کوتاه باید Confirmation صحیح داشته باشد؛ تست Confirmation نادرست باید رمز با طول صحیح داشته باشد.
- تست موفق ثبت‌نام باید نوع واقعی Hash را بررسی کند؛ CI و Docker Build پشتیبانی Argon2id را preflight می‌کنند.
- CI برای سرویس دارای PostgreSQL باید تست روی SQLite و PostgreSQL اجرا کند.
- تست نوشته‌شده، تست اجراشده و تست موفق سه وضعیت جدا هستند؛ گزارش باید دقیق باشد.

## ۹. چه چیزهایی پیش‌فرض نیستند؟

تا وقتی مسئله واقعی و توجیه‌شده به وجود نیامده، اضافه نکنید:

- لایه‌های Domain/Application/Infrastructure مجزا برای همه قابلیت‌ها
- Aggregate و Value Object برای هر جدول یا فیلد
- Generic Repository، Generic Service یا Base CRUD Framework
- Command، Query، Handler، Mediator یا Bus برای هر عملیات
- Read Model یا دیتابیس Read جدا
- DTO ورودی و خروجی برای هر endpoint
- Interface برای هر کلاس یا هر Facade لاراول
- Unit of Work برای عملیات ساده
- Event Sourcing یا Domain Event برای هر تغییر
- Outbox قبل از نیاز واقعی به انتشار Event قابل اتکا
- Factory، Manager یا Processor بدون مسئولیت مستقل
- Serviceهای موازی که فقط یکدیگر را wrap می‌کنند

## ۱۰. روند تغییر معماری

- تصمیم معماری مهم و پایدار در همین اسناد یا ADR ثبت می‌شود.
- تغییر API عمومی همزمان با OpenAPI به‌روز می‌شود.
- تغییر Event همزمان با Schema و نسخه آن انجام می‌شود.
- هر تغییر باید تست مرتبط و دلیل ایجاد abstractionهای جدید را مشخص کند.
- تغییرات کوچک، قابل بازبینی و با تست/CI پشتیبانی می‌شوند.
